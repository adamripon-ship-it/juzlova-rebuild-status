The situation

juzlova.cz was a small Czech recipe / marketing content site — traditional recipes and a few info pages (about, contact, where-to-find-us, prices). It is now down. There is no access to the original hosting admin or database, so nothing can be exported from the source; everything has to come from public archives.

The Wayback Machine holds ~1,246 snapshots going back to 2014. The task is to find the last capture taken while the site was still live, and recover its content and images.

Platform note discrepancy

Project notes described this as a "Shopify" site, but the captured URLs (/hello-world/, /category/uncategorized/, /author/…/, dated recipe slugs) are WordPress fingerprints, not Shopify. This doesn't change a content-only recovery — we copy text and images regardless of platform — but it is flagged so no effort is wasted chasing a platform-specific export. The recovery reads the rendered HTML, not any CMS internals.

Key ideas

  • Wayback CDX API — a queryable index of every capture. Used to list all archived URLs for the host (url=juzlova.cz*) and to pull the homepage's capture history with size and content digest per snapshot.
  • Size / digest as a down-detector — when a live page is replaced by a parking page, its byte size and content digest change sharply. That's how the 2026 captures were flagged as the down state and 2025-12-09 as the last live one.
  • Content vs. presentation — the Webflow rebuild recreates the look by hand; recovery only needs to preserve the content (words + images) plus a visual reference to build against.

Approach

Option C: produce a clean content package — one Markdown file per page, an images/ folder, and an inventory manifest — plus a working local mirror to serve as a visual reference during the Webflow rebuild. Work proceeds automatically (the owner delegated the decision and asked for auto-continue on resume); the only hard prerequisite is pinning the right snapshot first, so a wrong choice doesn't poison everything downstream.

⚠ The honest caveat

The Wayback Machine only has what it actually crawled. If a recipe image or an entire page was never snapshotted near 2025-12-09, it is simply gone — no recovery method reaches it. The package will therefore have documented holes rather than being a guaranteed 100% faithful copy. The inventory will make every gap explicit so nothing silently goes missing.

Why recover from the Wayback Machine instead of the original host?

The site is down and there's no access to the original hosting admin or database. The public web archive is the only surviving source of the content.

Why Webflow, and not just restore the old CMS?

The owner chose Webflow — a visual builder — for a fresh, clean rebuild. The goal is a new site, not resurrecting the old (WordPress-shaped) infrastructure. So the recovery hands over content, not server code.

Why content-only (Option C) rather than a full site clone?

Because the rebuild happens by hand in Webflow, the valuable output is clean, reusable content (Markdown + images) plus a visual reference to build against — not layout code that Webflow regenerates anyway. Option C also includes a working local mirror, so there's a faithful picture to copy from.

What does "done" look like?

/Users/adam/Juzlova/ holds a Markdown file per real page, an images/ folder, an inventory manifest listing every page and image with its source Wayback URL (and any gaps), and a working local mirror — enough for the owner to start the Webflow rebuild without ever returning to the Wayback Machine.
